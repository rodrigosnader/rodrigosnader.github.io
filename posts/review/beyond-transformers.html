Beyond Transformers

The Transformer won for real reasons — parallelism, stability, predictable scaling. But its core design creates inefficiencies that compound at scale. Fourteen architectural bets on what could come next, across six axes: input, compute, memory, plasticity, continuous learning, and system design.

2026 · Mar 15 · 22 min read · Interactive · AI

The Transformer architecture has dominated AI since 2017. Its core mechanism — self-attention — compares every token to every other token in the context window, producing O(n²·d) cost per layer. This scales poorly: a 128k-token context means an attention matrix with over 16 billion entries per head, per layer.

Before proposing alternatives, it's worth understanding why Transformers won:

  • Parallelism. Unlike RNNs, all tokens can be processed simultaneously during training. This maps perfectly to GPU hardware.
  • Gradient stability. Residual connections and layer normalization give Transformers remarkably stable training dynamics at scale.
  • Predictable scaling. Scaling laws (Kaplan et al., Hoffmann et al.) showed that performance improves predictably with compute, data, and parameters. This made billion-dollar training investments less risky.
  • Mature ecosystem. Hardware, compilers, frameworks, and optimization techniques are all built around Transformers.

These are real advantages. Any alternative architecture must either match them or offer gains large enough to justify the switching cost.

That said, the Transformer's design carries structural inefficiencies that become increasingly costly at scale. Processing 100,000 tokens to answer a question that depends on 20 is not a feature — it's a limitation of the architecture. The ideas below explore directions that could address these limitations.

They are organized into six thematic axes, ordered from input processing to system-level design. Each includes prior work, open problems, and an honest feasibility assessment.

Axis 1 — Input representation

1A. Dynamic context-dependent tokenization

Problem. Current tokenization (BPE, Unigram) is fixed after training. The same text always produces the same tokens regardless of context. This is statistically rigid — the optimal granularity of tokenization depends on the task and content, but the tokenizer can't adapt.

Proposal. Replace fixed tokenization with a lightweight learned module that receives raw characters (or bytes) and dynamically groups them into variable-length units based on the current semantic context, trained end-to-end with the main model.

Prior work. Byte-level models (ByT5, MegaByte) process raw bytes directly. CANINE operates at the character level. MegaByte uses a patch-based approach to group bytes before a large model processes them. These demonstrate that learned grouping is viable but show mixed results on efficiency vs. subword baselines.

Open problem. Discrete grouping decisions create a non-differentiable boundary in end-to-end training. This requires techniques like Gumbel-Softmax or straight-through estimators, which add training complexity and can be unstable. The segmentation must also be stable enough that the main model can build consistent representations — noisy tokenization propagates as noise through the entire system.

Feasibility: near-term research — components exist, integration is the challenge.

1B. Bit-level universal input

Problem. Current models receive modality-specific inputs: text tokens, image patches, audio spectrograms. Each modality has its own encoder. This creates hard boundaries between modalities that the model must learn to bridge.

Proposal. Feed everything as raw binary sequences. Lightweight compression modules — likely specialized per modality structure — learn to group bits into meaningful units before the main model processes them. The main model's internal representation is homogeneous regardless of input modality.

Prior work. Perceiver and Perceiver IO (Jaegle et al., 2021) accept arbitrary input modalities and project them into a shared latent space. This is conceptually similar but operates on preprocessed features rather than raw bits.

Honest tension

If you need modality-specific compression experts, you've reintroduced structural bias per modality — which is precisely what current architectures already do. The gain would be that internal representations are homogeneous after compression, but the input stage is no longer "pure bits." This idea is philosophically appealing but practically converges toward existing multimodal architectures with extra steps.

Additional challenge. Sequence length explodes at the bit level. A 1024×1024 RGB image is ~25 million bits. Even with aggressive compression, the input pipeline must reduce this by 3–4 orders of magnitude before the main model can process it.

Feasibility: requires paradigm shift — interesting as a research direction, but likely impractical as described. A more realistic version is learned compression that operates on bytes or small byte groups rather than individual bits.

Axis 2 — Adaptive compute

2A. Progressive internal context expansion

Problem. Transformers process the entire context window for every response, even when the answer depends on only a few recent tokens. A question like "what's your name?" costs the same as "summarize everything we discussed about authentication."

Proposal. The model starts by processing only the most recent portion of available context. It estimates whether this is sufficient to produce a confident response. If not, it progressively expands its active window — pulling in older context incrementally — until it reaches adequate confidence.

Key difference from RAG. The entire history is already available. The expansion is internal, not a retrieval call to an external system.

Prior work. Adaptive Computation Time (Graves, 2016) lets models decide how many computation steps to use per input. Universal Transformers apply variable depth per token. These address compute depth rather than context width, but the principle — allocate compute based on difficulty — is the same.

Open problem. How does the model estimate confidence without having seen the full context? If it uses a sub-model to estimate sufficiency, that's additional cost. If it relies on its own uncertainty on partial context, it may not know what it's missing. This is a chicken-and-egg problem that the proposal must address explicitly.

Feasibility: near-term research — the core mechanism (speculative processing with expansion) is implementable. The confidence estimation is the hard part.

2B. Dynamic sparse activation

Problem. In dense models, every parameter is computed for every token. Empirically, many neurons are barely active for any given input.

Proposal. A lightweight gating module analyzes each input and dynamically decides which blocks to activate. Unlike MoE, which has fixed expert boundaries, this allows activation patterns that vary per input.

Prior work. Mixture of Experts (Shazeer et al., 2017; Lepikhin et al., 2020) is the dominant approach to conditional computation. Switch Transformer routes each token to one expert. Routing networks and early-exit strategies also reduce per-token compute.

Honest tension

For real computational savings on current GPU hardware, sparsity must be structured — aligned with matrix dimensions so entire blocks can be skipped. But structured sparsity with fixed block boundaries converges toward MoE. "Fluid, overlapping activation patterns" sounds appealing but doesn't produce real savings on current hardware because matrix multiplications still execute at full size regardless of how many values are zero.

Possible resolution. Hardware is evolving. Structured sparsity support in GPUs (e.g., NVIDIA's 2:4 sparsity, Ampere architecture) is improving. If hardware catches up to fine-grained sparsity, the gap between "fluid" and "structured" narrows. But today, this idea is hardware-limited.

Feasibility: near-term research on structured variants; requires paradigm shift for truly fluid activation on current hardware.

Axis 3 — Memory architecture

This is the most interconnected axis. Rather than presenting separate ideas, it describes a progression from what's implementable today toward a longer-term vision.

Stage 1: Hierarchical compression before attention (implementable today)

Problem. A 100k-token context produces a massive attention matrix. Most comparisons are between tokens that have nothing to do with each other.

Proposal. Before running attention, apply a compression layer with a recency gradient:

  • Most recent tokens: preserved at full resolution (1:1)
  • Older tokens: grouped into compressed representations
  • Very old tokens: heavily summarized

Attention then runs on a much smaller sequence — for example, 2k recent tokens + 5k compressed representations instead of 100k raw tokens.

Prior work. Compressive Transformer (Rae et al., 2019) implements progressive compression with recency, storing compressed memories at multiple granularities. Landmark Attention uses special tokens as compressed summaries. Unlimiformer projects long sequences into a smaller set of memory slots. ALiBi and RoPE implement recency-based attention decay at the positional encoding level.

What this adds beyond prior work. Most existing approaches use uniform compression or fixed-size memory slots. The proposal here is a smooth, continuous gradient where compression increases proportionally with distance. The difference may be incremental rather than fundamental — this should be validated empirically.

Feasibility: implementable today — all components exist. The engineering challenge is tuning the compression curve.

Stage 2: Three-layer memory system (near-term)

Problem. Even with compression, a single mechanism can't efficiently handle information across all time scales.

Proposal. Separate memory into three explicit layers:

LayerMechanismCharacteristics
Short-termLocal attention (last N tokens)Full fidelity, high cost per token, small N
Medium-termRecurrent / SSM compressed stateCompressed, O(n) update cost, lossy
Long-termExternal structured memory (RAG-like)Large capacity, on-demand retrieval, retrieval cost per query

Prior work. Memorizing Transformers (Wu et al., 2022) add a kNN-based long-term memory. RETRO (Borgeaud et al., 2022) retrieves from a large database during generation. Hybrid models like Jamba (SSM + Transformer + MoE) combine attention with recurrent state but don't explicitly separate memory into tiers.

Open problems:

  • Medium-term compression is lossy. If critical information lands in the compressed zone, the model loses access to details it may later need.
  • Retrieval cost for the long-term layer is O(log n) with good indexing (not O(1)). Retrieved content then requires processing, adding latency.
  • The boundaries between layers (what stays in short-term vs. gets compressed) need careful tuning or learning.

Feasibility: near-term research — individual components exist (local attention, SSM, RAG). The integration and the learned boundary management are the research problems.

Stage 3: Native hierarchical long-term memory (longer-term vision)

Problem. External memory (RAG) is a workaround with real limitations: retrieval noise, latency, and a disconnect between "what the model knows" and "what it retrieves." But it also has genuine advantages — it's inspectable, updatable, auditable, and separates knowledge from computation.

Longer-term direction. If a model had true hierarchical memory built into the architecture, combined with continuous learning (see Axis 5), some RAG use cases could be absorbed natively. The model would:

  • Store important information in compressed long-term internal memory
  • Retrieve it through internal mechanisms
  • Update it through online learning
  • Forget irrelevant information through natural decay

Why this doesn't simply "replace RAG". Internal memory loses the auditability and inspectability of external memory. Internal retrieval also makes errors — they're just harder to debug. The practical direction is likely a hybrid: native memory for frequently-accessed, high-value patterns; external memory for large, evolving knowledge bases.

Feasibility: requires paradigm shift — requires solving hierarchical memory, dynamic capacity, and continuous learning simultaneously. Each is hard alone.

Axis 4 — Model plasticity

4A. Dynamic capacity

Problem. Current models have fixed parameter counts. A 7B model is always 7B, whether answering "hello" or reasoning through a complex proof.

Proposal. A model whose active capacity varies:

  • Activates more structure when complexity demands it
  • Compresses or deactivates regions that become irrelevant
  • Maintains a persistent state that evolves over time

Prior work. Adaptive Computation Time (Graves, 2016) allows variable computation depth. Early-exit strategies (DeeBERT, CALM) let tokens exit the network at different layers. Mixture of Depths (Raposo et al., 2024) routes tokens through variable numbers of layers.

Honest assessment. This idea is the vaguest in this collection. "Grows when complexity demands it" needs a concrete mechanism. Options include:

  • Activating dormant parameter blocks (like MoE but with variable expert count)
  • Dynamically adjusting network depth per input (Mixture of Depths)
  • Expanding/contracting hidden dimensions

The brain analogy (neural pathways forming and dissolving) is appealing but misleading — biological plasticity operates over days/weeks through physical growth, not through runtime compute allocation. A more honest framing: this is about adaptive compute allocation, not true structural plasticity.

Feasibility: near-term research for depth/width variation; requires paradigm shift for true structural growth/shrinkage at runtime.

4B. Variable-dimension embeddings

Problem. Every token is represented by a vector of fixed dimension (e.g., 4096 floats). The word "the" gets the same representational budget as a complex technical term.

Proposal. Allow embedding dimensions to vary based on the informational complexity of each token or concept.

Prior work. Matryoshka Representation Learning (Kusupati et al., 2022) trains embeddings where truncated prefixes remain useful, allowing variable-length representations at retrieval time. Product quantization and mixed-precision representations also address this partially.

Fundamental problem

This breaks standard matrix operations. You cannot multiply matrices with variable column widths on current hardware. This isn't a "challenge" — it's an architectural incompatibility. Possible workarounds (padding, packing, sparse representations) all either waste compute or require custom hardware support.

More realistic variant. Rather than truly variable dimensions, use a fixed large dimension but with learned sparsity — most dimensions are zero for simple tokens, full for complex ones. Combined with structured sparsity support in hardware, this could achieve similar goals without breaking matrix operations.

Feasibility: requires paradigm shift as described. The sparse-embedding variant is near-term research.

Axis 5 — Continuous learning

5A. Live models (online learning during deployment)

Problem. Current models are frozen after training. They don't learn from use. Every conversation starts from the same weights.

Proposal. Models that update specific parameters in real time during deployment, adapting to users, domains, and evolving information through selective, localized updates.

Prior work. Online learning and continual learning are mature research fields. Elastic Weight Consolidation (Kirkpatrick et al., 2017) protects important weights during sequential learning. Progressive Neural Networks (Rusu et al., 2016) add capacity for new tasks. Test-Time Training (Sun et al., 2020) updates model parameters using self-supervised objectives on each test input.

Central unsolved problem

Catastrophic forgetting. This isn't a footnote risk — it's the primary reason this doesn't work reliably today. When a model updates weights to accommodate new information, it degrades on previously learned tasks. All existing mitigation strategies (EWC, replay buffers, parameter isolation) involve significant tradeoffs between plasticity and stability.

Additional practical challenge. Even LoRA-style low-rank updates during inference require storing optimizer states and computing gradients, which significantly increases latency and memory. This is viable for slow background adaptation but not for real-time per-response updates.

Feasibility: near-term research for slow background adaptation (periodic fine-tuning, LoRA updates between sessions). requires paradigm shift for true real-time per-response learning.

5B. Multiple evolving loss functions

Problem. Current models are trained with essentially one loss function (next-token prediction), sometimes augmented by a small set of fixed auxiliary objectives. Complex intelligence arguably requires balancing many competing objectives simultaneously.

Proposal. Instead of a single static loss:

  • Multiple loss functions operating simultaneously (semantic coherence, factual consistency, task completion, self-consistency)
  • Dynamic weighting — the importance of each loss changes based on context and task
  • Self-generated objectives — the model learns to create its own sub-goals

Prior work. Multi-task learning uses multiple losses routinely. GradNorm (Chen et al., 2018) dynamically balances task weights during training. Intrinsic motivation in RL (curiosity-driven exploration, Pathak et al., 2017) lets agents generate their own reward signals. RLHF/DPO already introduce secondary optimization beyond next-token prediction.

Clarification on the brain analogy. The original motivation referenced the brain "developing its own loss functions." The brain's primary reward signals (dopamine, serotonin pathways) are largely hardwired by evolution, not self-generated. What does change over time is the learned association between stimuli and rewards — more analogous to learned reward shaping than to self-generated loss functions. The analogy should be stated more carefully.

Open problems:

  • Multi-objective optimization with dynamic weights is notoriously hard to stabilize.
  • "Self-generated objectives" risks reward hacking — the model optimizing for objectives that are easy to satisfy rather than genuinely useful.
  • Defining what the loss functions should be remains a human design problem.

Feasibility: near-term research for dynamic multi-objective training. speculative for truly self-generated objectives.

Axis 6 — System architecture

The practical endgame: small model + hierarchical memory + tools

The previous axes describe individual architectural innovations. This axis describes how they combine into a practical system.

Core thesis. A model in the range of 15–30B active parameters, combined with:

  • Hierarchical memory (Axis 3, Stages 1–2)
  • External tools (code execution, calculators, search, verification)
  • A reasoning loop (planner, self-reflection, chain-of-thought)

could match the effective capability of much larger monolithic models across many tasks.

Why this range? Below ~7B, models lack sufficient internal capacity for robust reasoning, compositional generalization, and reliable tool use. Between 7B and 30B, there's a significant jump in reasoning stability and robustness. Above 30B, the marginal gains per parameter diminish — especially when memory and tools handle knowledge retrieval and verification.

What the model becomes. A cognitive processor — not a knowledge store. It handles:

  • Semantic understanding
  • Short-range reasoning
  • Tool orchestration
  • Query formulation for memory retrieval

Knowledge, long-range reasoning, and verification are externalized.

What this doesn't solve. Robustness under ambiguity, graceful degradation when retrieval fails, and the meta-skill of knowing when to use which tool. These correlate with model scale in ways that are not yet fully understood.

On active/continuous input. Any model can receive continuous input streams — this is a deployment decision, not an architectural one. The architectural contribution comes from the other axes: efficient processing of continuous input (Axis 2), hierarchical storage of ongoing experience (Axis 3), and learning from observation (Axis 5). The "always-on model" is an integration challenge built on top of these capabilities.

Feasibility: implementable today with current open models (Llama, Qwen, Mistral at 20B–30B range) + existing memory/tool frameworks. The ceiling is engineering quality, not architectural impossibility.

Dependencies:

  • Axis 2 (Adaptive Compute) benefits from Axis 1 (better input representation reduces sequence length)
  • Axis 3 (Memory) benefits from Axis 2 (adaptive compute decides what to store vs. discard)
  • Axis 5 (Continuous Learning) requires Axis 3 (somewhere to store what's learned)
  • Axis 6 (System) integrates all other axes

Independent research tracks:

  • Axes 1 and 4 can be pursued independently
  • Axes 2 and 3 are tightly coupled
  • Axis 5 benefits from all others but can be researched in isolation

What would prove these ideas wrong

For these proposals to be worth pursuing, they need to be falsifiable. Here's what would indicate each direction is a dead end:

  • Adaptive compute (Axis 2): if models with fixed full-context processing consistently outperform adaptive variants even when controlling for total FLOPs, the overhead of deciding what to process exceeds the savings from skipping.
  • Hierarchical memory (Axis 3): if information compressed into medium-term memory degrades quality on downstream tasks more than the compute savings justify, compression is a net negative.
  • Model plasticity (Axis 4): if variable-capacity models fail to outperform fixed-size models of equivalent average compute, the routing/allocation overhead doesn't pay for itself.
  • Continuous learning (Axis 5): if catastrophic forgetting remains unsolvable without losing more capability than the adaptation gains, frozen models with periodic retraining are strictly better.
  • Small model + system (Axis 6): if robustness and reliability scale with parameter count in ways that external systems fundamentally cannot compensate for, there's a hard floor on model size that memory and tools can't lower.

These are empirical questions. The answers may differ by domain, task type, and deployment context.

Closing

The Transformer's dominance is earned: parallelism, stability, predictable scaling, and ecosystem maturity are real advantages that any competitor must contend with.

But the Transformer's core design — uniform processing of all tokens, fixed capacity, no persistent memory, no adaptation — creates inefficiencies that compound as we push toward longer contexts, more modalities, and continuous interaction.

The directions outlined here are not a single unified architecture. They are research bets at different levels of the stack, with different timelines and different risk profiles. Some are implementable today. Some require hardware that doesn't exist yet. Some may turn out to be dead ends.

The testable claim is this: a system combining a 15–30B parameter model with hierarchical memory, adaptive compute, and external tools can match the effective capability of models 10× its size across a meaningful set of tasks — at a fraction of the cost.

If that claim holds, it changes who can build and deploy capable AI systems. If it doesn't, we learn something concrete about why scale matters in ways that architecture cannot replace.

Either outcome advances the field.

Some of these ideas overlap with active research directions (cited inline). Others are novel combinations or extensions. All remain to be validated empirically. Prior work citations are representative, not exhaustive.
